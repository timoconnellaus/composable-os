# Start a client app

Describes extension contract version 1. For the platform version a repo is on, read
`platform.version` in its `product.ts`.

## When to use it

A company wants its own product on Composable OS: a website where its customers sign in, a mobile
app, the staff admin and MCP that come with the host. Either there is no repository yet (create
one), or the company already has a site or an app (adopt it, moving nothing).

The host (records, rules, sign-in, the staff admin) is deployed from a verified platform release.
The client repo holds only the company's apps, its own extensions (`extensions/`), copied blocks
and `product.ts`. It never holds platform code and never opens a database. The host is named for
the company's product at its first install (`<id>-app`, `<id>-runner`, the `<id>` database;
`names` in `product.ts` overrides them) and shows the product's `label`. A host that exists keeps
its names: nothing deployed is renamed. A product may declare **environments** (a staging host and
a live host side by side in one account, `environments` in `product.ts`): each is its own host,
`<id>-staging-app` and so on, while `live` keeps `<id>-app`.

## The steps

1. **New or existing?**
   - **New:** `npm create composable-os <dir> -- --label "<Name>"` (that is `cos create <dir>`;
     add `--with-mobile` for the Expo app). The id comes from `<dir>`. It writes the repo, runs
     `git init`, and generates each app's typed client.
   - **Existing:** at its root, `pnpm dlx @composable-os/cli init --id <id> --label "<Name>"
     --web <dir> --mobile <dir>` (leave out an app it does not have). Without `--id` and `--label`
     both come from the folder's name. It adds `product.ts`, `skills/`, each app's typed client and
     host module (`<app>/src/composable-os/customer.ts` and `host.ts`; the mobile app also
     `secure-store.ts`), a `pnpm-workspace.yaml` when the apps are in folders of their own, and the
     client-repo rules in `AGENTS.md`. It changes no file that exists without showing the diff
     first and applies the diffs only with `--yes`: read them, then run it again with `--yes`. An
     adopted web app keeps its Worker (`web.worker` is its name) and its own deploy
     (`web.deploy: "own"` in `product.ts`). `--packs ticketing` turns packs on; `--envs
     staging,live` declares environments. It never adds the `HOST` binding to the top level of
     the site's config: a site that deploys itself (perhaps on every push) would fail its deploy
     binding to a host that does not exist yet. Under an environment of the site's own config with
     the same name it shows the binding as a diff; the rest it prints, to add only after
     `cos deploy --env <name>` has made that host.
2. **Read `AGENTS.md`.** Its rules hold for everything after this.
3. **Choose the packs.** `product.ts` lists the packs that are on (`packs: ["ticketing"]`). A
   release carries every pack (its `packs.json`); list only what the request needs. An empty list
   is base records only (people, organisations, activities, tasks), and each signed-in customer
   can always read their own Person (`me.get`). `cos deploy` refuses a pack the release does not
   carry, before it touches the account: that is a gap in the platform (say so), not something to
   work around. Every pack listed is installed on the host at its first boot after the deploy,
   with no admin step, whatever the pack's `optional` says (that is only for the CRM's own
   catalogue); one added later is installed by the next deploy. Removing a pack from the list
   deletes nothing: it stays installed with its records; an admin may disable it (its records stay).
   - **Gatekeepers** (outbound email, payments) and their settings go in `product.ts`
     (`gatekeepers`, or per environment): `"email-send": { ALLOWED_SENDER_DOMAINS: "…" }`,
     `payments: { STRIPE_ACCOUNT: "…" }`. Secrets never go there: `cos deploy` prints each missing
     one and the `wrangler secret put` command a person runs. `PAYMENTS_FAKE_PROVIDER: true` only in
     an environment marked `live: false` (its signing secret is generated by `cos deploy`). See
     `docs/deploying.md` (Gatekeepers and their settings).
4. **Install:** `pnpm install` at the root.
5. **The web app** reaches the host only through `HOST`, a service binding to the host's
   `ClientApp` entrypoint: already in the template's `apps/web/wrangler.jsonc`, shown as a diff by
   `cos init` for an existing Worker. Its host module (`apps/web/src/host.ts` in the template,
   `src/composable-os/host.ts` when adopted) has what a page needs: `customerApi(env, request)`
   (the typed client for the customer the request comes from), `signedInCustomer`, the sign-in
   routes `authRoute` serves (`POST /auth/code`, `/auth/sign-in`, `/auth/sign-out`), and
   `withSessionKept`, which keeps customers signed in. **The template already has a public page,
   a sign-in page, an account page from `me.get` and sign-out**: for a request like "members sign
   in and see their account" there is nothing to add, unless the platform's sign-in block is
   wanted (the `add-block` skill).
   - **An adopted site with data of its own** (its own D1, KV or R2): it keeps them and keeps
     deploying itself. Customers' records live in the host. What moves into the host, and when, is
     the company's decision: say so and do not move data or remove a binding yourself.
   - **Calls from the browser** (a block running in the page): the host module's
     `operationRoute(request, env, { allow: ["me.get", …] })`, served before the pages (the
     template's `src/server.ts` does). Same origin only, JSON only, only the operations `allow`
     names; it forwards the customer's cookie and the `Idempotency-Key` and nothing else. In the
     browser, `createCustomerClient({ baseUrl: location.origin })`.
   - **Astro with React islands** is a supported way to host web blocks: the page's server code
     uses the host module, and the islands call `operationRoute`. A site in a framework with no
     React at all calls the host from its server code only.
6. **The mobile app** (Expo) calls the host's public address over HTTPS with the same typed
   client. Its host module (`apps/mobile/src/host.ts`, or `src/composable-os/host.ts` when adopted)
   has `hostSession({ hostUrl, store, deviceName, random })` with `requestCode`, `signIn` (the host
   answers the emailed code with a device session's tokens, kept in the secure store, never a
   cookie), `api` and `signOut`. `random` is the app's secure random source
   (`src/secure-random.ts`, expo-crypto): React Native has no `crypto`, and the module refuses to
   start without it. The host's address is `expo.extra.hostUrl` in `app.json`.
   - **Staff with a pack role** (a coach at the door): list the role in `product.ts`
     (`mobile: { dir, roles: ["ticketing.door"] }`) and run `pnpm cos client generate`: it writes
     `src/client/roles/ticketing.door.ts`, with only that role's operations. Never put the staff
     client in the app. Staff sign in with `staffSession({ hostUrl, store: staffSecureStore,
     deviceName, random })` (`requestCode` and `signIn` by code, or `signInWithBrowser` with
     `redirectUri: "<scheme>://staff-sign-in"` and expo-web-browser's `openAuthSessionAsync` when
     staff sign in with Google or Cloudflare Access), then `staff.client(createTicketingDoorClient)`.
     The staff session has its own slot; a staff token goes only to the host.
   - **An adopted Expo app** on `expo/tsconfig.base` needs `allowImportingTsExtensions` and
     `noEmit` for the host module's `.ts` imports: `cos init` shows that change as a diff.
7. **Regenerate the clients** after changing `packs` or `extensions/`: `pnpm cos client generate`.
   `cos deploy` and `cos upgrade` do it too. `cos upgrade` also brings the host modules
   (`host.ts`, `secure-store.ts`, `secure-random.ts`) to the new template: one nobody edited is
   replaced; an edited one is left and its diff shown, to merge by hand. Commit
   `composable-os.lock.json`: it records what cos wrote.
8. **Deploy:** `CLOUDFLARE_API_TOKEN=... pnpm cos deploy`. Before anything in the account changes
   it runs `cos ext check` on every extension, type-checks every app that has a `tsconfig.json`
   (an app without one is not checked), and builds and checks the web app (a template web app
   must build to `dist/server/`; an adopted one with `web.deploy: "own"` is left to its own
   deploy). It prints `Checked: ...`, then deploys the host with the product's packs and the
   org's extensions, then the web app with its binding, and prints the web app's address. It sets
   customer sign-in up on the host (`CUSTOMER_AUTH_URL`, the web app's origin, and a
   `CUSTOMER_AUTH_SECRET` made once, never printed).
   - **With environments**, `pnpm cos deploy --env staging` (then `--env live`): with several and
     no `--env` it refuses and lists them. For an adopted site it prints exactly what the site's
     Worker config needs in that environment (the `HOST` binding's target and entrypoint).
   - **A Vite or Astro site picks its wrangler environment when it is built**, from
     `CLOUDFLARE_ENV`, not with `wrangler deploy --env`: `CLOUDFLARE_ENV=staging pnpm run build`
     then `wrangler deploy`. Built without it, a staging site binds to the live host.
9. **A person then does, by hand:**
   - open the host's address `/setup` to create the first staff admin;
   - connect an email-send connection (Settings → Integrations), then, as a human admin, in
     Settings → Users choose it as the host's mail connection and turn on "Send sign-in codes
     without review". Until then code requests (customers and staff) answer that sign-in is not
     set up. `cos deploy` does not do this, in any environment;
   - choose who may sign in as a customer (Settings → Users): only invited people (the default),
     invited people and anyone who has bought (a business that sells to guests who should see their
     tickets later), or anyone; and, for a business selling a plan with a free trial, also anyone
     starting a subscription (a new visitor confirms their address with a code on the plan: pass
     the subscribe block `signIn`). `cos deploy` never sets it;
   - invite staff (Settings → Users), with a pack role for a coach at the door;
   - for a custom hostname, `web.hostname` in `product.ts` (or `environments.<name>.web.hostname`)
     and its DNS;
   - the gatekeepers' secrets `cos deploy` named;
   - before opening the web app to the public, the rate limiting rule `cos` prints, on the web
     app's zone.

## The rules

- Call operations through the typed client only. Never give a web app the template deploys a D1,
  R2 or KV binding or a secret of its own; `cos deploy` refuses a build that has one.
- Rules live in the host: a screen never calculates a price, checks a capacity or decides what a
  customer may see.
- Customers sign in on the company's own hostname through the web app; staff use the admin on
  the host's address. Do not put the two on one hostname.
- **When the platform lacks something:** stop that part, say exactly what the platform needs (a
  behaviour, an operation, a gatekeeper, a pack in a release), and build the rest. Never work
  around it in client code.

## The check

`pnpm cos deploy` is the check: it ends with the web app's address after `Checked: ...`. Then a
person opens the web app, signs in with an emailed code and sees the account page.
